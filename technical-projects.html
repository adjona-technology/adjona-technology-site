Engineering & Technical Capability

Technical projects & engineering

Practical examples of Microsoft cloud engineering, automation and governance design.

Adjona develops internal solutions to explore, implement and validate approaches using Microsoft 365, Power Platform, Dynamics 365, Dataverse and related technologies. These projects show the technical architecture, design decisions and implementation methods behind that work.

They are not customer case studies and should not be read as evidence of production deployments for other organisations.

About these examples

The projects described here are internal Adjona engineering work. Where sample or test data is used, it is identified. Operational performance, security assurance and customer outcomes are not claimed unless they have been independently verified and documented.

Internal Adjona projectProject 01

Website enquiry and appointment management

Microsoft 365  ·  Power Automate  ·  Dataverse  ·  Dynamics 365 Sales

The problem

Enquiries arriving through website forms and appointment bookings become fragmented when they are handled across disconnected tools. Duplicated records, manual follow-up and unclear ownership make it harder for a small organisation to keep a reliable view of its prospective customers.

Technical approach

An internal workflow connects website enquiries and Microsoft Bookings with Dynamics 365 Sales and Dataverse through Power Automate. The architecture is intended to consolidate lead information, associate relevant appointments with the right record and support subsequent sales activity.

Design decisions

  • Checking for existing records before creating a new lead
  • Distinguishing relevant customer bookings from other appointment types
  • Mapping enquiry and booking information to appropriate CRM fields
  • Handling the relationship between leads and appointments
  • Controlling unnecessary duplication
  • Keeping the data structured so it can be reported on from Dataverse

Governance and security

Access permissions, data minimisation, retention, operational ownership and the handling of flow failures have to be considered alongside the workflow itself. A flow that works but fails silently, or keeps personal data longer than necessary, is not a finished solution.

What has been built

The workflow has been developed for Adjona's own operations.

How it has been tested

Documented test scenarios are not yet published on this page.

Known limitations

The design reflects one organisation's booking types and CRM fields. Another organisation would need its own field mapping, matching rules, permissions and retention decisions. No real enquiry or customer data is shown on this page.

What you can take from it

Connecting forms and bookings to a CRM is rarely just a connector problem. The work that makes it reliable is deciding how records are matched, who owns each step and what happens when something fails.

Internal Adjona projectProject 02

Charity intelligence and prospect research using MCP

API integration  ·  Python  ·  Model Context Protocol  ·  Dynamics 365

The problem

Identifying relevant charities and understanding their likely technology needs means drawing on several public sources. Manual research is repetitive and inconsistent, particularly when organisations need to be compared against defined eligibility or service criteria.

Technical approach

Adjona's internal Charity Prospector is a Model Context Protocol (MCP) server written in Python. It combines public charity and company data, public website and DNS signals and a Dynamics 365 integration, so that research can be carried out in a structured, repeatable way with explainable classification and controlled CRM operations.

Design decisions

  • Integrating with public data APIs, including the Charity Commission and Companies House
  • Normalising organisation information from multiple sources
  • Keeping observed evidence separate from inference
  • Applying explicit, named scoring and eligibility profiles
  • Explaining the basis of each classification
  • Using the charity number as the matching key to reduce duplicate records
  • Previewing every CRM change before it is written
  • Separating customer contexts and enforcing security boundaries between them

Governance and security

CRM writes are controlled rather than automatic: a proposed record is shown as a preview, a write needs explicit confirmation, and existing contact details are preserved by default. A separate development build is bound to a single customer context, runs read-only and refuses requests for scoring profiles that belong to another context, recording the refusal in an audit log.

What has been built

A working internal tool that retrieves public charity records, checks public DNS and website signals for the likely email and identity platform, applies scoring profiles, summarises filing history and governance indicators, and can create or update Dynamics 365 lead records.

How it has been tested

The solution has been through local development and automated testing, including work on multi-customer security controls. CRM writes have been checked by reading the record back after writing and confirming that an update keeps the same record rather than creating a duplicate. Boundary tests have confirmed that out-of-scope profile requests are refused with a structured response.

Known limitations

The tool uses public information only. DNS and website signals suggest which platform an organisation probably uses. They do not show how its Microsoft 365 tenant is configured, and they say nothing about its security or compliance status.

Lookups are keyed to charities registered with the Charity Commission for England and Wales, so CICs and other company structures are not currently covered. Scores reflect the criteria in the selected profile and are read alongside the supporting evidence, with a person confirming any qualification.

What you can take from it

When AI tools are connected to business systems, the important design questions are about control: what the tool may read, what it may change, how changes are confirmed and how one customer's information is kept separate from another's.

Internal Adjona projectTest data onlyProject 03

Dynamics 365 and Power BI operational reporting

Dataverse  ·  Dynamics 365 Sales  ·  Power BI

The problem

Small organisations can hold operational and commercial information in a CRM without having an accessible, consolidated view of activity, pipeline and follow-up priorities.

Technical approach

A Power BI report built on Dynamics 365 Sales and Dataverse data. The aim is to make CRM activity easier to understand for routine oversight, without users needing to open individual records.

Design decisions

  • Identifying the relevant CRM tables and relationships
  • Defining suitable reporting measures
  • Avoiding misleading counts and duplicate aggregation
  • Representing enquiry and appointment activity
  • Keeping reporting separate from day-to-day record management

Governance and security

Reports can expose information to people who would not see it in the CRM itself. Refresh arrangements, report access and how reports are distributed need to be decided as carefully as the measures.

What has been built

A Power BI report drawing on Dynamics 365 Sales and Dataverse tables.

How it has been tested

The report currently uses development and test records only.

Known limitations

Any figures shown are synthetic or test data. They do not represent real Adjona enquiries, revenue, customers or commercial pipeline. Refresh, access and distribution arrangements would need to be set for each organisation.

What you can take from it

A useful report starts with agreeing what each number means and where it comes from. Otherwise a dashboard can look authoritative while counting the same thing twice.
